# WatchTower user guide

This guide explains how to configure and operate WatchTower through its web interface. The options visible to a user depend on administrator status and delegated access grants.

## First sign-in

Open the public WatchTower address and sign in through the configured identity provider. An administrator sees every application, workspace, feed, setting, and access-control option. Delegated users see only the resources and actions allowed by their grants.

For a new installation:

1. Open **Settings** and confirm the public address.
2. Add an application.
3. Create a workspace and assign the application.
4. Run **Refresh checks**.
5. Review the application's findings, lifecycle status, and source links.

## Dashboard and status

The Overview page summarizes monitored applications. Named workspaces restrict the view to their assigned applications, while All Applications shows the complete visible inventory.

Select a status card to filter the current list. Selecting more than one status combines them, and selecting a card again removes that filter.

- **Red** means an application has a high-confidence High or Critical finding, a CISA known-exploited vulnerability, or a release cycle past end of life.
- **Yellow** means no red condition exists and end of life is within 90 days.
- **Green** means configured checks succeeded, the mapped release is supported, and no High, Critical, or known-exploited finding was returned.
- **Unknown** means a source failed, a lifecycle cycle could not be matched, or lifecycle information is not configured.

A green status is not proof that an application is vulnerability-free. New vulnerabilities can be unpublished, unscored, incorrectly mapped, or absent from the configured sources.

Select an application row to view installed and available releases, assessment reasons, vulnerability findings, vendor-feed evidence, and source links. Confirm remediation decisions against the linked vendor advisory.

## Applications

### Add an application

1. Select **Add application**.
2. Enter a clear display name, optional vendor, and installed version.
3. Select **Choose CPE** and complete the vulnerability mapping.
4. Select **Choose source** and complete the lifecycle mapping, or provide a manual end-of-life date and source URL.
5. Add optional vendor security and release-note URLs.
6. Use version overrides only when the lifecycle source does not provide reliable release targets.
7. Select the workspaces and feeds that should include the application.
8. Save the application and refresh checks.

The application ID is generated by WatchTower and cannot be changed. Editing an application that belongs to several workspaces changes the shared application everywhere.

### Edit an application

Open the application details and select **Edit application**. Update the installed version immediately after an upgrade so vulnerability ranges, lifecycle matching, notifications, and acknowledgements are evaluated against the deployed release.

Review the CPE and lifecycle mappings whenever the product name, edition, release family, or vendor changes.

## CPE vulnerability mappings

The CPE dialog maps an application to the product identifiers used by NVD.

1. Open an application's editor and select **Choose CPE**.
2. Search **Any field**, or narrow the query by part, vendor, product, version, or edition.
3. Leave **Include deprecated CPEs** disabled unless researching a legacy identifier.
4. Select the result that represents the installed product, not merely a similarly named component.
5. Review every parsed component and warning.

You may also paste a complete CPE 2.3 name and select **Parse CPE**.

- **Use this product** is recommended for most applications. WatchTower ignores the selected CPE version, searches the product, and evaluates the installed application version against NVD affected ranges.
- **Use this exact CPE** retains the selected version, edition, and qualifiers. Use it only when those fields are required to distinguish the installed product.

Select **Test this mapping** before saving. Review the candidate and applicable vulnerability counts, representative matches, deprecation warnings, version conflicts, and overly broad qualifiers. A successful test shows what the mapping finds; it does not guarantee the product identity is correct.

Select **Use selected mapping**, then save the application.

## Lifecycle mappings

Lifecycle mappings connect an application with endoflife.date release-cycle data.

1. Open the application editor and select **Choose source**.
2. Search by product, alias, or tag and optionally filter by category.
3. Review the suggested results. WatchTower uses the application name, vendor, and CPE as ranking hints.
4. Select a product and inspect its release cycles, latest releases, maintenance status, and end-of-life dates.
5. Select **Test this mapping** to match the installed version with a release cycle.
6. Review warnings when the installed version cannot be matched or the lifecycle product's published identifiers disagree with the vulnerability CPE.
7. Select **Use this product**, then save the application.

If endoflife.date does not list the product, close the dialog and use a manual end-of-life date with a vendor lifecycle URL. Manual values should come from an authoritative vendor source and should be reviewed periodically.

## Workspaces

Workspaces group applications for navigation, delegated access, and notification routing. One application can belong to several workspaces.

1. Select **Add / edit workspace**, or open a workspace and select **Edit workspace**.
2. Enter a recognizable workspace name.
3. Select the applications that belong to it.
4. Add notification recipients when that workspace should send email.
5. Save the workspace.

Use workspaces for meaningful operational boundaries such as teams, environments, business services, or customer groups. Because applications are shared records, use separate application entries when two environments run different installed versions.

## Vendor and advisory feeds

Feeds add reusable vendor evidence to one or more applications. WatchTower supports RSS, Atom, JSON, HTML, and public GitHub repository advisory sources.

1. Open **Feeds** and select **Add feed**.
2. Enter a display name and public HTTPS URL.
3. Choose a format or leave automatic detection enabled.
4. Add product aliases found in the source.
5. Select whether the source contains security, release, lifecycle, or multiple categories.
6. Associate the feed with applications.
7. Select **Test feed** and review the normalized preview.
8. Save and enable the feed.

Use **Collect now** to update one feed without waiting for the next scheduled scan. Disable a feed when it is temporarily unreliable, and remove it only when its associations are no longer needed.

Feed data is treated as untrusted. WatchTower blocks private and metadata-service destinations, validates redirects and DNS results, limits responses, strips markup, and never executes feed content. A valid feed can still contain inaccurate applicability information, so confirm findings with the vendor.

## Email notifications

Email delivery has two parts: global delivery settings and recipients assigned to each workspace.

### Configure delivery

1. Open **Settings** and enable email delivery.
2. Enter the SMTP host, port, sender address, time zone, and local send hour.
3. Choose SSL/TLS, required STARTTLS, or no TLS requirement according to the mail service.
4. For authenticated SMTP, enter the name of the environment variable containing the username. The password must already be available through the mounted `SMTP_PASSWORD_FILE` configured by the container administrator.
5. For a trusted-IP relay, select **Use an unauthenticated SMTP relay**.
6. Enter a test recipient and select **Send test email**.
7. Save the settings after the test succeeds.

### Add recipients

Edit a workspace and enter comma-separated notification addresses. Leaving the field blank disables email for that workspace.

Each workspace receives its own message containing alerts due for its applications. An application in several workspaces can generate a message for each workspace. Initial Critical and known-exploited findings can send immediately; scheduled High, lifecycle, and reminder messages wait for the configured local delivery window.

Acknowledgement links require confirmation. Acknowledging an application stops repeat reminders for that application and workspace until the alert clears or its installed version changes. It does not remove the application from the dashboard.

## General settings

Open **Settings > General** and configure the public protocol, hostname, and web port used in notification links. These values must describe the address recipients can reach, which may differ from the container's internal listener.

When WatchTower is behind a reverse proxy, use the public HTTPS hostname and port. Saving an incorrect address can produce unusable email links.

## Access control

Administrators use **Access Control** to map exact identity-provider claims to WatchTower roles.

### Add an identity mapping

1. Select **Add mapping**.
2. Enter a display name.
3. Choose the claim source: `groups`, `roles`, `realm_access.roles`, or `resource_access.roles`.
4. Enter the exact, case-sensitive claim value.
5. Leave the mapping enabled and save access control.

Use **Current administrator session** to inspect claims supplied for the signed-in administrator or Access Administrator.

### Add a grant

1. Select **Add grant** and choose an identity mapping.
2. Choose a global, workspace, application, or feed scope.
3. Select one or more roles available for that scope.
4. For a scoped grant, select the resources it covers.
5. Select one or more identity mappings for verification and inspect their combined effective permissions.
6. Save access control after the proposed grants behave as intended.

Available responsibilities include access administration, workspace viewing and management, workspace membership, workspace application editing, notification management, application viewing and editing, feed viewing and editing, global feed management, and manual scan operation.

### Verify and preview access

Select **Include in verification** on any combination of identity mappings and grants. All saved grants are selected initially; clear individual grants to test narrower proposed combinations. Select no identity mappings to represent an authenticated user whose claims match no configured mapping.

- **Verify selected access** calculates permissions from the current form, including changes that have not been saved. It lists every contributing grant and the effective global, application, workspace, and feed permissions.
- **Preview selected access** reloads WatchTower with those permissions enforced by the server. A persistent banner identifies the preview and provides the exit action.

Permission Preview is always read-only. It shows resources and controls available to the selected access, but the server rejects every mutation until the preview is exited. The original privileged session remains authenticated underneath the preview so the banner can always restore it.

When previewing proposed changes, WatchTower keeps an expiring draft in the current browser tab. Exiting Permission Preview returns to Access Control with the same unsaved identity mappings, grants, and verification selections. The draft is removed after a successful save, when Access Control is left outside a preview, when the tab's browser session ends, or after eight hours.

The global **Access Administrator** role can manage mappings, ordinary grants, verification, and Permission Preview without receiving access to applications, feeds, scans, logs, or settings. Only a protected administrator authenticated through the configured administrator group or `WatchTower.Administrator` role can add, remove, or change Access Administrator assignments.

Permissions from matching grants are combined. Workspace Application Editor applies to every current and future application assigned to that workspace. Workspace Membership Manager is separate because changing membership can expand a user's access.

Keep at least one tested protected-administrator path before narrowing access. Unmatched authenticated users receive no application access.

## Refreshing checks

WatchTower scans at startup when saved results are missing or stale and then runs on its configured interval. Users with scan permission can select **Refresh checks** to run an immediate refresh.

The browser checks for updated results while open. Large inventories without an NVD API key take longer because WatchTower respects the public NVD rate limit.

## Logs and troubleshooting

Open **Logs** to inspect recent scans, feed requests, errors, and configuration changes. Newest entries appear first.

Audit entries identify the time, action, resource, changed fields, and signed-in identity. Notification recipient changes do not record addresses, and credential values are never logged.

When investigating a problem:

1. Confirm the latest scan time and source status.
2. Open the affected application and review its mapping, assessment reasons, and sources.
3. Check **Logs** for request, parsing, authorization, or delivery errors.
4. Test the CPE, lifecycle mapping, feed, or email delivery in its editor.
5. Ask the container administrator to review runtime logs when startup, networking, or mounted secrets are involved.

## Direct YAML editing

WatchTower stores configuration as YAML and detects external changes, but direct editing is discouraged. The UI validates values and relationships, preserves immutable identifiers, applies permission checks, and creates attributable audit records.

Use the interface for normal administration. Direct file editing should be limited to recovery or carefully controlled maintenance with a current backup and a clear understanding of the stored schema.
