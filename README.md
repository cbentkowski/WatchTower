# Vulnerability dashboard

Track installed application versions against vendor advisories, NVD CVEs, CISA's Known Exploited Vulnerabilities catalog, and endoflife.date lifecycle data.

## Run

1. Use **Add application** in the sidebar to enter each installed app and version. The form requires a name, version, vulnerability mapping, and either a lifecycle product or a manual end-of-life date. WatchTower generates an immutable UUID. Choose the vulnerability mapping to open Cartographer's in-app CPE dialog, where you can search multiple NVD fields, paste a complete CPE 2.3 name, select product or exact mapping, review warnings, and test representative vulnerability matches before saving. Choose the lifecycle source to search endoflife.date by product, alias, category, or tag, preview release cycles, and test the installed-version match. Results are ranked using the application, vendor, and selected CPE. You can also edit `config/applications.yaml` directly; its included examples are disabled.
   For products not listed by endoflife.date, use `eolDate: YYYY-MM-DD` and `lifecycleUrl:` with the vendor's support page. You may add `vendorBulletinUrl:` to link the product's security posts in its detail view.
2. Use **Add / edit workspace** to create groups and select their applications, or edit `config/workspaces.yaml` directly. An application can belong to multiple workspaces. Overview shows summary cards and only applications needing action; the built-in All Applications workspace shows the full inventory.
   Each named workspace page also has **Edit workspace** for changing its name, application membership, and notification recipients when permitted. Open an application and choose **Edit application** to update its display name, installed version, CPE mapping, lifecycle settings, source links, release overrides, or workspace memberships. Application and workspace UUIDs are permanent and appear as reference labels in their editors. Existing slug IDs are converted to UUIDs at startup and retained as `legacyId` values.
   On workspace pages, click a status card to filter the inventory. Multiple selected statuses combine with OR. Click a selected status to remove it, or click **Monitored Applications** to show all applications.
3. Open **Feeds** to add reusable vendor RSS, Atom, JSON, HTML, or GitHub repository advisory sources and associate them with applications.
4. Run `npm ci`, then `node server.mjs` with Node.js 22 or newer. Configure OIDC as described below first. For a private local development instance, set `AUTH_DISABLED=true` explicitly.
5. Open `http://127.0.0.1:4173`.

The server reads configuration from the `config` directory. Existing `cpeVendor`, `cpeProduct`, and optional `cpeEdition` fields are migrated automatically to a canonical `cpeName` and `cpeMode`; compatibility fields remain available to the scanner and existing integrations. Product mode queries the selected part, vendor, and product with a wildcard version, then evaluates the installed application version against NVD affected ranges. Exact mode retains every selected CPE qualifier and warns when its version conflicts with the installed version. It scans at startup when the saved results are missing or stale, then scans at the top of every hour. You can also click **Refresh checks** or send `scan` to the server console. The browser checks for updated results every minute while open. The latest scan is saved to `data/status.json` and reused after a restart if it is less than an hour old; the dashboard does not retain historical scans. Notification state is saved separately in `data/notifications.json`. No API keys are required. NVD requests are spaced to respect its public rate limit. For larger inventories, set `NVD_API_KEY` in the server process environment to speed up checks and mapping tests.

Use **Logs** in the left navigation to inspect recent scans, feed requests, errors, and configuration changes. Application, workspace, feed, access-control, General, and email changes produce audit entries with the timestamp, action, target ID, changed fields, and the signed-in user's OIDC issuer, subject, and display name. Notification recipient changes are noted without recording addresses; SMTP credential values are never logged. With `AUTH_DISABLED=true`, the actor is labeled as a local development session because no user identity is available. The server checks configuration YAML every 30 seconds and logs changes made outside the web interface as unattributed filesystem changes, without logging file contents. External application, workspace, or feed changes trigger a fresh scan when automatic scans are enabled. Logs are saved in `data/logs.jsonl` with one rotated previous file when it grows beyond 5 MB. Feed checks require outbound HTTPS access from the running server process.

## Vendor feeds

Feed definitions are stored in `config/feeds.yaml`, while normalized entries and HTTP cache metadata are stored in `data/feeds.json`. Feed IDs are immutable UUIDs. A feed may serve multiple applications, and an application may use multiple feeds. The scanner recognizes security, release, and lifecycle events, retains source links and confidence, and marks ambiguous security applicability for review instead of declaring an application safe. High-confidence affected ranges can produce vulnerability findings. Release entries can update latest-version targets, and dated lifecycle entries can update support status.

Choose **GitHub advisories** and enter a public repository URL such as `https://github.com/istio/istio/security/advisories`; WatchTower uses GitHub's public repository-advisory API. Use **Test feed** to preview inert normalized records before relying on the source, or **Collect now** to update that feed's persisted cache without waiting for the hourly scan.

Feed content is untrusted. WatchTower permits only public HTTPS destinations on port 443, rejects URL credentials and private, loopback, link-local, internal, and metadata-service addresses, validates every redirect and DNS result, and applies strict time, redirect, entry, content-type, and response-size limits. XML, JSON, and HTML are converted to bounded plain text. Scripts, styles, HTML tags, event handlers, and control characters are discarded; feed content is never evaluated, imported, or inserted into the interface without output escaping. A Content Security Policy provides an additional browser-side boundary.

## Email notifications and settings

Open **Settings** in the left navigation. **General** stores the public protocol, hostname, and web port in `config/general.yaml` for links in notification emails. Until saved, the form suggests the address currently used in your browser. Once saved, the configured address remains fixed; choose an address recipients can reach. General address fields are always required when saving Settings. **Email delivery** is disabled by default and stores SMTP host, port, TLS choice, sender address, time zone, and the local hour when reminders may be sent in `config/smtp.yaml`. While disabled, its fields may be blank. Enabling authenticated delivery requires SMTP host, port, From address, SSL/TLS or STARTTLS, a username environment variable name, and a readable, nonempty SMTP password secret file. Store the password in a host file named `smtp-password`, mount it read-only into the container, and set `SMTP_PASSWORD_FILE` to its container path, such as `/run/watchtower-secrets/smtp-password`. Only the file path is an environment variable; the password never enters Pelican's variable store, WatchTower YAML, or the web interface. Settings verifies that the mounted file exists and contains a value before allowing authenticated email to be enabled. The file is read again for every delivery and test, so password rotation does not require rebuilding the image or resaving Settings.

For a trusted-IP SMTP relay, select **Use an unauthenticated SMTP relay**. WatchTower then sends without SMTP credentials, even if environment variable names remain in `config/smtp.yaml`. Choose SSL/TLS, STARTTLS, or no TLS requirement to suggest port 465, 587, or 25 respectively. The port remains editable for a relay that uses a different port. Enter a test recipient and choose **Send test email** to validate the currently entered values without saving them.

Edit a named workspace and add comma-separated **Notification emails** to enable email for that workspace. Recipients are stored in `config/workspaces.yaml`. Each workspace gets one message containing all alerts due for its applications; an application in multiple workspaces can generate one alert in each. A high or critical vulnerability triggers an initial needs-action email, then a reminder every seven days. An application within 30 days of end of life triggers one warning; after end of life it triggers a weekly reminder. Acknowledgment links open a confirmation page and only stop reminders after the recipient confirms. Acknowledgment applies to that application in that workspace until its alert clears or its installed version changes. The application continues to appear in the dashboard.

The hourly scan also evaluates notifications, so no separate cron job is needed. Mail is sent only after the configured local send hour, once the relevant alert is due. Keep one running instance with persistent storage for `config/general.yaml`, `config/smtp.yaml`, `config/workspaces.yaml`, and `data/notifications.json`; the notification state prevents duplicate reminders and preserves acknowledgments across restarts. If SMTP is incomplete or delivery fails, the alert remains due and the next scan retries it.

## Container deployment

The included `Dockerfile` builds a self-contained Node 22 image. Its hourly scheduler runs in the application process, so it needs no host cron job, sidecar, or platform schedule. Mount a persistent volume at `/home/container`; the image copies starter YAML files into `/home/container/config` on first run, and the app writes `/home/container/data/status.json` after each scan. When upgrading an existing deployment, the entrypoint automatically moves legacy YAML files from `/home/container` into `/home/container/config`. The image listens on port 4173 by default and honors `PORT` or `SERVER_PORT`. Run `docker compose up -d --build` to use the included `compose.yaml` for a local container deployment.

HTTP is the default internal listener. To terminate HTTPS in WatchTower itself, mount a PEM certificate chain and its matching PEM private key read-only, then set `TLS_ENABLED=true`, `TLS_CERT_FILE` to the mounted certificate path, and `TLS_KEY_FILE` to the mounted key path. Both files must be readable and nonempty, the key must match the certificate, and the server requires TLS 1.2 or newer. WatchTower fails startup instead of falling back to HTTP when enabled TLS is invalid. Certificate rotation requires restarting the container. The private key is never accepted through YAML, the web interface, or an environment-variable value.

The listener protocol is independent from **Settings → General**. Keep General set to the public protocol, hostname, and port that users and the OIDC provider reach. For example, Caddy or an Istio sidecar can expose public HTTPS while WatchTower keeps its default HTTP listener. Native HTTPS is intended for direct TLS termination or TLS passthrough. OIDC remains the authentication mechanism; WatchTower does not request client certificates.

For Pelican, build and push the image to a registry your node can pull from, then create a custom egg using that image. Set startup to `node /opt/watchtower/server.mjs`, stop to `^C` or `^SIGINT`, and start completion text to `Vulnerability dashboard:`. Give it one TCP allocation; the app reads Pelican's `SERVER_PORT`. Pelican persists `/home/container`, including the `config` directory and scan data. No Pelican schedule is needed. See [Pelican's custom egg](https://pelican.dev/docs/eggs/creating-a-custom-egg/) and [custom Yolk](https://pelican.dev/docs/eggs/creating-a-custom-yolk/) instructions.

For other container hosts, attach persistent storage at `/home/container`, expose the selected port, and keep one app instance running. The YAML files, latest scan, and notification state are local files; without persistent storage they are lost when a container is replaced.

## OIDC sign-in

WatchTower supports Microsoft Entra ID and Keycloak through OpenID Connect. Configure these environment variables in the container or deployment platform; do not put the client secret in YAML or the image:

```text
OIDC_ISSUER=https://login.microsoftonline.com/<tenant-id>/v2.0
OIDC_CLIENT_ID=<application-client-id>
OIDC_CLIENT_SECRET=<client-secret-value>
OIDC_BASE_URL=https://home.thebentkowskis.org
```

For a deployment platform that cannot conceal environment variables, store the client secret in a read-only file and set `OIDC_CLIENT_SECRET_FILE=/run/watchtower-secrets/oidc-client-secret` instead of `OIDC_CLIENT_SECRET`. Set only one of these two options. Pelican mounts do not appear in its file manager or SFTP and can be attached read-only, making a host directory mounted outside `/home/container` suitable for this purpose. The container user must have permission to read the mounted file. WatchTower reads the file for each OIDC flow and automatically rebuilds its provider configuration when the value changes, so rotating this file does not require a container restart.

Store the protected administrator group object ID in another read-only mounted file and set `OIDC_ADMIN_GROUP_ID_FILE=/run/watchtower-secrets/admin-group-id`. The file contains only the exact Entra group object ID or Keycloak group claim value. This value is never editable through Settings, Access Control, or `rbac.yaml`. WatchTower reads it during every successful login, so the file can be rotated without rebuilding the image. The identity provider must include the value in the ID token's `groups` claim.

For Keycloak, use `OIDC_ISSUER=https://<keycloak-host>/realms/<realm>` and that realm's confidential client ID and secret. Register `https://home.thebentkowskis.org/auth/callback` as the **Web redirect URI** in either provider. Enable the standard authorization code flow. The issuer must have a trusted HTTPS certificate. The public URL must be HTTPS except for local loopback development. Terminate TLS at a reverse proxy and forward requests to WatchTower's HTTP port; the container does not serve TLS itself. Set General's public address to the same HTTPS hostname and port 443 so email links use it.

When all four variables are present, WatchTower requires sign-in for the dashboard and every API, including settings, logs, refreshes, and inventory changes. A missing value fails startup instead of leaving a partially configured login. Sign-in uses the authorization code flow with PKCE, state, and nonce. Sessions are held in server memory for eight hours in an HTTP-only, SameSite cookie. Restarting the process signs everyone out; run one instance unless session storage is added. The email acknowledgement link remains a token-based confirmation page accessible to recipients without sign-in.

WatchTower grants unrestricted access when the OIDC `groups` claim contains the value stored in `OIDC_ADMIN_GROUP_ID_FILE`. For compatibility, it also recognizes the predefined `WatchTower.Administrator` value in an OIDC role claim. Administrators can open **Access Control** to map exact OIDC group or role claim values to WatchTower grants. A grant selects one identity mapping, a global, workspace, application, or feed scope, one or more resources, and one or more standard roles. Feed Viewer reads selected feed configuration and evidence; Feed Editor can modify, enable, disable, test, and refresh selected feeds; global Feed Manager can add, remove, edit, and associate every feed. Application Editors may associate feeds they can view with applications they can edit. Permissions from all matching grants are combined. Workspace Application Editor applies to every current and future application in its workspace; editing a shared application changes it in every workspace. Workspace Membership Manager remains separate because membership changes can expand access. Unmatched authenticated users receive no resource access. In Microsoft Entra, create an app role with display name `WatchTower Administrator`, allowed member type **Users/Groups**, and value `WatchTower.Administrator`; then assign the `WatchTower Administrators` group to that app role under the enterprise application's **Users and groups** page. In Keycloak, map a role with the same value into the ID token's `roles` claim.

Optionally set `OIDC_REQUIRED_ROLE=WatchTower.User` to require a separate baseline role before anyone can enter WatchTower. When enabled, administrators must receive both `WatchTower.User` and `WatchTower.Administrator`. Use Entra's **Assignment required** setting or the equivalent provider control to restrict who can sign in. Access mappings and grants are stored in `config/rbac.yaml`; claim values can come from `groups`, `roles`, `realm_access.roles`, or the configured client's `resource_access` roles. With no OIDC configuration, the server refuses to start unless `AUTH_DISABLED=true` is set explicitly for a private development instance.

## Status rules

- **Red:** one or more high-confidence vendor-feed or NVD high/critical findings, a CISA known exploited CVE, or the release cycle is past end of life.
- **Yellow:** no red condition and the release cycle reaches end of life within 90 days.
- **Green:** all configured checks succeeded, release is supported, and no high/critical or known exploited CVEs were returned.
- **Unknown:** source check failed, lifecycle cycle could not be matched, or lifecycle source was not configured.

Associated vendor and GitHub advisory feeds provide primary evidence when they contain explicit affected ranges. Jira Software Data Center and Confluence Data Center also use Atlassian's version-specific Security Vulnerability API. GitLab Enterprise Edition uses GitLab's official patch release feed. NVD remains the fallback, and CISA KEV is checked alongside all primary sources for known exploitation.

Application details show the newest release overall, the newest patch on the installed release line, and the newest supported LTS release when the lifecycle source designates one. These release targets come from endoflife.date's cycle data and link to vendor release notes when `releaseUrl` is supplied. Verify availability and upgrade paths with the vendor before upgrading. For a product without lifecycle data, optional `latestVersion`, `latestBranchVersion`, and `latestLtsVersion` fields can be supplied in the YAML inventory.

This is a triage view. A green result reflects the data available at check time and correct CPE mapping; it does not prove the product is vulnerability-free. CVEs may not yet be scored or published, and a zero-day report without a CVE or CISA listing will not be detected automatically. Vendor security pages are linked for manual review. Verify affected versions and vendor advisories before remediation. The YAML parser intentionally supports only the flat fields shown in the example, not the full YAML language.
